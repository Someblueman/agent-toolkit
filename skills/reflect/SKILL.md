# Reflect

Retain only lessons that would change a future decision. A reflection can produce no updates;
do not manufacture guidance to make the session look productive.

## Find the lesson

- Use the relevant conversation, actual changes, command results, and user corrections. Inspect
  only the history needed to understand this task; do not mine unrelated sessions by default.
- For each candidate lesson, identify the observation, its cause if supported, and the future
  action it would change. Distinguish verified facts, explicit preferences, and tentative
  interpretations. One verified command correction can be useful; one failure does not justify
  a universal process rule.
- Check current code and existing guidance before retaining a claim. A workaround may already
  be obsolete, a lesson may already be documented, or the real problem may be an implementation
  defect. Do not substitute a new instruction for a needed code fix.

## Choose the smallest useful destination

| Lesson | Destination |
|---|---|
| Verified project command, constraint, or convention | Existing project documentation; a scoped AGENTS.md only when agents need it routinely |
| Reusable procedure that changes how a task is performed | The relevant skill's maintained source |
| Task progress, attempt history, or temporary constraint | The existing task plan or notes |
| Personal preference or permission policy | Propose separately unless the user explicitly requested that change |
| Unsupported explanation or possible pattern | Report as tentative; do not promote to instructions |

Prefer correcting or replacing existing text over appending a new rule. Keep AGENTS.md short
and link to detailed documentation where appropriate. Locate the source of truth before editing
installed or generated guidance; do not patch a managed copy or vendor package as a shortcut.
Use the environment's supported memory mechanism only when explicitly asked to update memory
and within its rules. Reflection alone is not permission to write personal memory.

## Apply within scope

If the user asks for analysis or suggestions, return concrete proposed edits without applying
them. If the user asks to capture lessons or update named guidance, make the supported updates
within that scope. Reuse authorization already given; ask only when the destination or change
would materially expand it. Do not change permissions, install recurring automation, publish,
or launch a new campaign as a consequence of reflection.

Validate changed commands, links, or skill structure as appropriate. When a behavioral rule is
changed, explain which observed failure it addresses and what remains untested; structural
validation does not prove better agent behavior. Preserve unrelated edits and follow applicable
commit and installation conventions for authorized updates.

Report what was learned, the evidence supporting it, and what was changed or proposed, with
links. Mention rejected or tentative lessons only when they affect a decision. Avoid creating
a separate lesson ledger, retrospective file, or approval workflow when the existing destination
and a short response suffice.
